## Next 16.4.2 公开 API 的具体缺口

2026-10-23 阅读官方当前 v16.4.2 文档，并核对安装包 `node_modules/next/dist/server/web/spec-extension/unstable-cache.d.ts`、`revalidate.d.ts` 和只读实现：

- [unstable_cache](https://nextjs.org/docs/app/api-reference/functions/unstable_cache) 提供 `unstable_cache(callback, keyParts, { revalidate, tags })`。刷新 callback 仅收到调用参数，得不到上一条共享缓存值；没有公开任意 get / put / compare-and-set API。函数参数属于缓存键，把旧 snapshot 当参数传入会改变键，也不能解决首次从共享缓存读取旧元数据的问题。
- [fetch](https://nextjs.org/docs/app/api-reference/functions/fetch) 的 force-cache 缓存 HTTP 请求结果，只有 200 被存储。它不是标准化 snapshot 与可更新冷却元数据的通用存储接口；请求头差异还会改变匹配键。
- [revalidateTag](https://nextjs.org/docs/app/api-reference/functions/revalidateTag) 是失效接口，允许的调用上下文是 Server Functions / Route Handlers；不能把它当作 T07 SSR 服务里通用写入接口。`updateTag` 仅 Server Actions。
- [use cache](https://nextjs.org/docs/app/api-reference/directives/use-cache) 默认使用进程内运行缓存，在 Serverless 下不保证跨请求持久；remote handler 需要另选真实共享后端，也没有自动补足本卡的旧元数据业务接口。

因此，直接用 `unstable_cache(fetchMet)` 做 15 分钟刷新不能在刷新前读取旧 Last-Modified / Expires，304 也无旧 snapshot 可继承。失败抛错虽可保留 Next 的旧值，却不能持久写入新的 429 Retry-After；返回失败值又会覆盖旧成功 snapshot。这是尚未解决的实现契约缺口，不能用注入 fake get/set 测试或进程 Map 声称已经接入真实平台。
